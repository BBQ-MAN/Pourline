# Device Verification — 실기기 검증

단위 테스트는 명세가 맞다는 가정 위에서만 의미가 있다. 공식 문서에는 CRC 세부와 무게 단위가 빠져 있으므로 실기기 캡처 없이는 코덱이 맞는지 알 수 없다. 이 절차는 사용자가 저울을 조작하고 메인 에이전트가 안내·기록한다. 캡처 판별과 명세 반영은 `scale-protocol` 스킬의 몫이다.

## 로그 형식(모든 캡처 공통)

```
RX FFF1 A55A01010009<payload 18자리><CRC 4자리>   # 저울 → 앱 (알림 원본, 받은 그대로 한 줄에 한 알림)
TX FFF2 A55A030D0000<CRC 4자리>                    # 앱 → 저울
EV <설명>                                          # 사용자가 한 동작, 연결 상태, MTU 등
```

- `EV` 줄로 "지금 100 g 추를 올렸다" 같은 동작을 남긴다. 동작과 프레임을 이어 볼 수 없으면 무게 단위를 확정할 수 없다.
- nRF Connect 값(`(0x) A5-5A-01-…`)은 접두어와 대시를 지우고 연속 hex로 옮긴다(`crc_probe.py`는 대시 표기도 받지만 파일 형식을 통일한다).
- 알림 하나는 한 줄이다. 프레임이 둘로 쪼개져 왔으면 두 줄로 그대로 적는다. 합치지 않는다.
- 파일은 `_workspace/04_device_{probe}_{scenario}.log`.

## 프로브 A — 앱 없이 원시 프레임 캡처 (구현 전에 먼저)

준비: 휴대폰에 nRF Connect for Mobile, 저울 켜기, 알려진 무게의 물체(추, 또는 다른 저울로 잰 물 컵).

1. **광고**: SCAN 탭에서 저울을 찾아 원시 광고 데이터(RAW)와 이름, Manufacturer Data, 광고된 서비스 UUID를 그대로 옮겨 적는다(`EV ADV ...`).
2. **연결**: 자동 MTU 요청을 끈 상태로 CONNECT하고 `EV MTU=<값>`을 적는다. 서비스 `0xFFF0`과 `0x180A`가 보이는지 확인하고 Device Information의 Model/Firmware/Manufacturer 값을 적는다. 본딩 요청이 뜨는지 적는다.
3. **알림 구독**: `0xFFF1` Notify를 켠다. 아래 동작마다 `EV`를 적고 그 사이의 알림 hex를 5개 이상 옮긴다.
   - 빈 저울 영점 상태, 그대로 2분 방치(전송이 멈추는지, 절전 직전 동작)
   - 알려진 무게 W g를 올린 상태(W를 `EV`에 적는다)
   - 물체를 내려 음수가 되게(영점 후 들어 올리기)
   - 저울 버튼으로 단위 g → oz 전환(같은 무게를 올린 채), 다시 g
   - 저울 버튼으로 타이머 시작 → 정지 → 초기화
   - 물을 천천히 부으며 유량 값 변화
4. **CRC 판별**: `python3 -I .claude/skills/scale-protocol/scripts/crc_probe.py --file <로그>`. 종료 코드 0(조합 하나)이면 출력된 `--variant … --order … --start …`를 기록한다. 3(모호)이면 3번 동작을 더 캡처한다. 1이면 원시 로그를 `scale-protocol` 분석으로 넘긴다.
5. **명령 쓰기**: 4번 결과로 영점 명령을 만든다: `crc_probe.py --build 03 0D "" --variant <4번> --order <4번> --start <4번>`. nRF Connect에서 `0xFFF2`에 Write without response로 보내고(`TX` 줄로 기록) 뒤따르는 0x01 무게가 0이 되는지(Dot에는 숫자 화면이 없다), `0xFFF1`로 opcode `03` cmd `0D`, data `01` 응답이 오는지 적는다.
6. **분할 확인**(MTU 23 상태 유지):
   - 현재 이름을 읽어 둔다: `crc_probe.py --build 02 0C "" <4번 인자>`.
   - 13~16바이트 이름으로 쓴다(`--build 03 0C <이름 UTF-8 hex> <4번 인자>`). 24바이트를 넘는 쓰기를 저울이 받는지(응답 성공·실패·무응답) 적는다.
   - 다시 읽어 응답이 알림 몇 개로 오는지 적는다.
   - 원래 이름으로 되돌린다.

결과는 메인 에이전트가 `_workspace/04_device_probeA_result.md`에 요약하고, 오케스트레이터 1단계(워크플로 `protocol-verify.js`, `deviceLogs` 인자)로 넘긴다.

## 프로브 B — 디버그 앱 시나리오 (구현 후)

준비: `android-build-verify`의 `references/env-setup.md` 4절(adb), `./gradlew installDebug`.

logcat 수집은 끝나지 않는 명령이므로 둘 중 하나로 한다.

```bash
adb logcat -c                                                           # 시나리오 시작 전 비우기
# (a) 시나리오 끝에 덤프
adb logcat -d -s TimemoreBle:V > _workspace/04_device_b_<scenario>.log
# (b) Bash run_in_background로 실시간 수집하고, 사용자가 시나리오 완료를 알리면 TaskStop
adb logcat -s TimemoreBle:V > _workspace/04_device_b_<scenario>.log
```

Dot에는 숫자 화면이 없다(protocol.md D-1, 2026-11-03 사용자 확인). 저울 쪽 값은 화면이 아니라 원시 프레임(0x01 무게·타이머 필드), 공식 TIMEMORE 앱, 알려진 무게로 확인한다. 저울 화면을 보라는 기준을 새로 쓰지 않는다.

| ID | 시나리오 | 통과 기준 |
|----|----------|-----------|
| B1 | 첫 실행 권한 허용 → 스캔 → 연결 | 10초 안에 연결, 같은 물건을 공식 앱으로 잰 값이나 알려진 무게와 앱 무게 표시가 같음(같은 시각 0x01 원시 프레임 값도 기록) |
| B2 | 권한 거부, 다시 묻지 않음 | 해당 화면 상태와 설정 이동 버튼 |
| B3 | 블루투스 끈 상태로 시작, 실행 중 끄기·켜기 | 꺼짐 상태 표시, 켜면 자동 재연결 |
| B4 | 앱에서 영점 | 응답 성공 로그 뒤 0x01 무게와 앱 무게가 0 |
| B5 | 앱에서 타이머 시작·정지·초기화, 저울 버튼으로도 조작 | 앱 타이머 상태와 0x01 타이머 필드(늘어남·멈춤·0) 일치 |
| B6 | 저울 전원 끄기 → 켜기 | 재연결 중 표시 → 자동 재연결, 끊긴 동안 마지막 값이 "멈춤"으로 표시 |
| B7 | 저울에서 단위 oz로 변경 | 앱 표시가 올바르게 변환됨(또는 명세대로 처리) |
| B8 | 레시피 따라 실제 추출 3분 | 단계 진행, 유량 그래프, 끊김 없음, 기록 저장 |
| B9 | 추출 중 화면 회전, 홈 갔다 오기 | 연결·타이머 유지 |
| B10 | 10분 연속 측정(저울 active 구간) | active 구간의 알림 누락 비율(10 Hz 기대 대비 RX 수) 1% 미만, 메모리 증가 없음 |
| B11 | 기록 CSV 내보내기 | 파일 열림, 헤더와 단위가 명세와 같음 |
| B12 | TalkBack 켜고 추출 | 숫자를 매 알림마다 읽지 않음, 상태 변화(끊김·영점·타이머)를 알림(D9a·D9b) |

- 실패한 시나리오는 로그 파일과 함께 `_workspace/04_device_results.md`에 적는다.
- 원시 프레임이 명세와 다르면 프로토콜 문제, 프레임은 맞는데 화면이 틀리면 앱 문제로 나눠 오케스트레이터에 넘긴다.
- 실기기에서 확인하지 않은 시나리오를 통과로 적지 않는다.
