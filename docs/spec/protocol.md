# Timemore Dot 프로토콜 명세
원문: `docs/protocol/source/Timemore Black Mirror SCALE BLE Protocol.md` v1.0.3 · 실기기: 프로브 A (TES017, 펌웨어 `v1.0.4`, macOS bleak) · 마지막 갱신: 2026-10-29

근거 표기:
- `원문 §절 Lx-y` = 원문 파일의 절과 줄 번호.
- `log:N` = `_workspace/04_device_probeA_mac.log`의 N번째 줄. `결과` = `_workspace/04_device_probeA_result.md`.
- 로그는 캡처 4회, 실제 연결 3회(log:2, log:6739, log:10770) 분량이다. 캡처마다 `+초` 시각이 0부터 다시 시작한다(경계 log:6737, log:10766, log:10768). 두 번째 재시작(log:10767)은 기기를 찾지 못해 연결이 없다.
- 실기기 로그와 원문이 충돌하면 로그를 따르고 원문 내용을 함께 적는다(`충돌` 표시). 펌웨어 판이 다르면 동작이 다를 수 있다.

상태 정의:
- **확정**: 원문이 명시했거나 실기기 캡처로 확인했다.
- **미확정**: 원문이 침묵하거나 모호하고 실기기로도 확인하지 않았다. 앱은 후보대로 구현하되 결과를 신뢰하지 않는다.
- **해당 없음**: 이 기기(TES017 v1.0.4)에서 일어나지 않음을 실기기로 확인했다.
- **미확정(수정됨, 재검증 필요)**: 교차 검증에서 반박되어 검증 근거로 고친 항목. 다음 검증에서 다시 확인한다.

## 1. GATT

| ID | 서비스 | 특성 | 128비트 UUID | 속성 | 앱 용도 |
|----|--------|------|--------------|------|---------|
| G-1 | custom 0xFFF0 | — | `0000fff0-0000-1000-8000-00805f9b34fb` | — | 저울 서비스 |
| G-1 | custom 0xFFF0 | Uplink 0xFFF1 | `0000fff1-0000-1000-8000-00805f9b34fb` | Notify | 저울→앱 모든 프레임 수신(G-1a). CCCD(`00002902-0000-1000-8000-00805f9b34fb`)에 `01 00` 써서 구독(G-1b) |
| G-1 | custom 0xFFF0 | Downlink 0xFFF2 | `0000fff2-0000-1000-8000-00805f9b34fb` | Write without response | 모든 앱→저울 프레임 송신 |
| G-2 | Device Information 0x180A | Model Number 0x2A24 | `00002a24-0000-1000-8000-00805f9b34fb` | Read | 기기 식별(`TES017`, G-3) |
| G-2 | Device Information 0x180A | Firmware Revision 0x2A26 | `00002a26-0000-1000-8000-00805f9b34fb` | Read | 진단 로그에 펌웨어 판 기록 |
| G-2 | Device Information 0x180A | Manufacturer Name 0x2A29 | `00002a29-0000-1000-8000-00805f9b34fb` | Read | 진단용 |
| G-7 | 미상 | ff02 / ff03 | 서비스 `5833ff01-9b8b-5191-6142-22a4536ef123` | write / notify | 쓰지 않는다 |

- 서비스 UUID 0x180A = `0000180a-0000-1000-8000-00805f9b34fb`.
- DIS 문자열은 UTF-8, 널 종료 없음(G-2). 앱은 받은 바이트 전체를 문자열로 디코딩한다.
- G-5(확정): Read·Write 응답은 FFF1 Notify로 온다. 응답은 대개 무게 프레임 뒤에 붙어 같은 알림으로 온다(F-10).
- G-6(확정, macOS 실측): 본딩 없이 연결한다. macOS 연결 3회 모두 페어링 요청 없이 구독했다. 영점은 연결 1·3, 타이머는 연결 1에서 성공했다.
- G-7: 원문에 없는 서비스다. 앱은 서비스 탐색에서 무시한다. FFF0이 없을 때 이 서비스만으로 저울로 판단하지 않는다.

연결 순서(GATT-1, 앱 규칙): 연결 → 서비스 탐색 → FFF1 CCCD 구독 → 0x06 단위 읽기 → 0x05 배터리 읽기 → 0x02 타이머 읽기 → (선택) 0x2A24·0x2A26 읽기.

- 0x02 타이머 읽기(GATT-1, 앱 규칙): 연결·재연결 직후 Read 응답(opcode `02`, C-02-1)은 앱 상태를 저울과 맞추는 데에만 쓴다. 타이머 이벤트(시작·일시정지·리셋)로 보지 않는다. 연결 후 타이머를 조작하기 전 첫 Read 응답은 `03` 리셋이었다(C-02-4). 전원을 켠 직후에도 `03`인지는 미확정이다. 예: 추출 중 저울 전원을 껐다 켜면 Read 응답이 `03`이어도 추출을 끝내지 않는다. Read 응답과 앱 상태가 다를 때 어느 쪽을 따를지는 앱 설계(architecture.md 8.2절)가 정한다. 원문에는 이 처리 규칙이 없다.
- TES017 v1.0.4는 0x02 Notify를 보내지 않는다(C-02-2, C-02-3). 타이머 상태는 앱의 Write 응답과 0x02 Read로만 바뀐다.

## 2. 프레임

### 2.1 오프셋 표 (F-1 ~ F-5)

| 오프셋 | 길이 | 필드 | 형식 | 비고 |
|--------|------|------|------|------|
| 0 | 2 | header | `A5 5A` | 고정 (F-1) |
| 2 | 1 | opcode | uint8 | `01` Notify, `02` Read, `03` Write (F-5) |
| 3 | 1 | cmd | uint8 | 3절 명령 |
| 4 | 2 | length | uint16 BE | payload 바이트 수 (F-3, F-4). 부호 없음은 원문에 명시가 없어 미확정(바이트 수라 음수 불가로 추정). 실측 최대 12, 앱 상한 64(F-10a)라 부호 해석은 결과에 영향 없음 |
| 6 | n | payload | 명령별 | n = length |
| 6+n | 2 | CRC | 2바이트 | 수신은 검사하지 않음, 송신은 `00 00` (2.2절) |

전체 프레임 길이 = 6 + length + 2. payload 없는 요청은 8바이트다. CRC 자리를 빼고 보내지 않는다(F-12).

방향과 opcode:
- 저울→앱 Notify: opcode `01`.
- 앱→저울 Read 요청: opcode `02`, length 0. 저울 응답도 opcode `02`.
- 앱→저울 Write 요청: opcode `03`. 저울 응답도 opcode `03`, length 1, payload `00`/`01` (C-W-1).

### 2.2 CRC (F-6 ~ F-9)

| 항목 | 값 | 상태 |
|------|-----|------|
| 저울 송신 CRC | 항상 `00 00` | 확정, 펌웨어 v1.0.4 (F-8) |
| 저울 수신 CRC 검사 | 하지 않음(`0000`·`FFFF` 모두 처리) | 확정, 펌웨어 v1.0.4 (F-8) |
| 앱 수신 | CRC 2바이트를 읽고 버린다. 검사하지 않는다 | 확정 (F-8) |
| 앱 송신 | CRC 2바이트에 `00 00` | 확정 (F-9) |
| 원문 기재 | CRC-16/IBM, poly `0x8005`, init `0xFFFF`, 범위 헤더~payload | 원문 §3 L62-64. 실기기와 충돌 (F-6, F-7) |
| CRC 바이트 순서 | big(벡터 `crc.byteOrder`) | 미확정. 원문 §3 L68의 일반 규칙(다중 바이트 big-endian)에서 추정. 실기기 CRC 값이 `0000`/`FFFF`뿐이라 순서를 가를 수 없다. v1.0.4에서는 앱 동작에 영향 없음. CRC를 쓰는 펌웨어가 나오면 프로브 A로 0이 아닌 CRC를 캡처해 확인 |

- 원문과 실기기의 충돌: 원문 v1.0.3은 CRC 계산을 적지만 펌웨어 v1.0.4는 CRC 자리를 `0000`으로 채운다. `crc_probe.py --file _workspace/04_device_probeA_mac.log`는 poly 0x8005 후보 조합 중 모든 프레임에 맞는 것이 없다고 판정했다. 로그를 따른다.
- 송신 값을 `0000`으로 정한 이유: 저울이 보내는 값과 같고, 실측한 모든 송신이 `0000`으로 성공했다(F-9). 원문 후보(MODBUS)로 계산한 값은 실기기에 보낸 적이 없다.
- 다른 펌웨어 판: 미확정이다. CRC를 쓰는 펌웨어가 나오면 이 절과 벡터를 다시 쓴다. 그 전까지 앱은 0x0000이 아닌 CRC를 받아도 프레임을 버리지 않는다.

예(F-7a, 확정): 영점 요청 `A55A030D00000000`.

구현 규칙: 코덱은 "수신 CRC 검사 안 함, 송신 CRC 0x0000"을 상수 한 곳에 둔다.

### 2.3 수신 재조립 (F-10)

알림 경계와 프레임 경계가 같다고 가정하지 않는다. 실측에서 알림 하나에 프레임이 최대 4개 붙어 왔다(F-10). 앱은 FFF1 알림 바이트를 버퍼에 이어 붙이고 다음 규칙을 반복한다.

1. 버퍼에서 `A5 5A`를 찾는다. 앞의 바이트는 버린다. 찾지 못하면 마지막 바이트가 `A5`일 때만 그 1바이트를 남기고 나머지를 버린다.
2. 헤더부터 6바이트가 모이지 않았으면 다음 알림을 기다린다.
3. length를 읽는다. length > 64이면 헤더가 가짜라고 보고 헤더 첫 바이트(`A5`)만 버리고 1로 돌아간다. 64는 앱 상한이다(F-10a 미확정, 앱 방어 규칙). 실측 최대 length는 12다.
4. 6 + length + 2바이트가 모이지 않았으면 기다린다.
5. CRC는 검사하지 않는다(F-8). `CrcMismatch`는 내지 않는다.
6. 프레임을 꺼내 3절대로 디코딩하고 버퍼에서 제거한다. 버퍼에 남은 바이트로 1을 반복한다.
7. 프레임은 맞지만 cmd별 payload 길이가 3절과 다르면 `LengthMismatch`를 보고하고 그 프레임만 버린다. 고정 길이 cmd(0x01, 0x02, 0x05, 0x06, Write 응답)에만 적용한다. 가변 길이 응답(0x0C 이름, 0x10 펌웨어)은 검사하지 않는다(미확정, 앱 방어 규칙. 실측에서 길이 불일치는 한 번도 없었다).
8. 알 수 없는 opcode/cmd 조합(예: 0x04, C-04-1)은 `Unknown`으로 보고하고 버린다. 연결은 유지한다.
9. 연결이 끊기면 버퍼를 비운다.

### 2.4 송신 (F-11, F-12)

- 앱은 프레임 하나를 FFF2 Write without response 한 번으로 보낸다. 프레임은 항상 CRC 2바이트(`00 00`)까지 포함한다(F-9, F-12).
- 프레임이 현재 MTU−3바이트를 넘는 경우(MTU 23에서 20바이트 초과: 이름 13~16바이트 쓰기) 저울이 나뉜 쓰기를 받아들이는지는 원문 언급도 실측도 없어 미확정이다(F-11). 앱은 나눠 쓰지 않고 `PayloadTooLarge`로 거부한다(architecture.md 4.1 F-11 행, 앱 규칙). MVP는 이름 쓰기(0x0C W)를 쓰지 않는다. MTU 증가 뒤 나눠 쓰기는 앱 규칙이 아니며, 이름 쓰기를 넣을 때 실측 뒤 다시 정한다. 확인 방법: 휴대폰 nRF Connect, MTU 23에서 13~16바이트 이름 쓰기(프로브 A 분할 단계).
- 앱은 Write 요청을 한 번에 하나씩 보내고 응답(C-W-1)이나 시간 제한(C-W-2)을 기다린다. 같은 cmd를 연달아 보내면 응답이 어느 요청의 것인지 가를 수 없다. 1 ms 간격으로 두 프레임을 보낸 실측에서 응답이 하나만 왔다(log:3673-3677). 다만 그중 하나가 CRC 없는 7바이트 프레임이어서(F-12) 연속 송신 자체가 원인인지는 가르지 못했다.

## 3. 명령

공통: 모든 프레임은 2절 형식이다. 아래 payload 오프셋은 payload 시작(프레임 오프셋 6) 기준이다. 아래 예시 hex의 CRC는 모두 `0000`이다. 벡터 `expect`는 raw 값을 담는다. 단위 변환은 3.1의 변환식으로 별도 테스트한다.

### 3.1 0x01 무게·유량·타이머 (scale→App, Notify)

opcode `01`, cmd `01`, length `0x0009` (C-01-1). 주기 100 ms, 연결 중 계속 (C-01-12).

| payload 오프셋 | 길이 | 필드 | 형식 | 범위 | ID |
|----------------|------|------|------|------|----|
| 0 | 4 | weightRaw | int32 BE (2의 보수) | 원문 없음(용량 미확정, C-01-14) | C-01-2, C-01-14 |
| 4 | 2 | flowRaw | int16 BE (2의 보수) | 0~999 (원문·실측) | C-01-5, C-01-7 |
| 6 | 2 | timerSec | uint16 BE | 0~3599 | C-01-8 |
| 8 | 1 | overload | uint8 | `0` 정상, `1` 한계 초과 | C-01-10 |

실측 예: `A55A01010009000005AA00000000000000` → weightRaw 1450(145.0 g), flowRaw 0, timerSec 0, overload 0 (log:13439).

앱 변환식. 입력은 (raw, 현재 단위)다.

| 현재 단위 | 무게 | 유량 | 상태 |
|-----------|------|------|------|
| g | `weightRaw / 10.0` g | `flowRaw / 10.0` g/s | 확정(C-01-3, C-01-5) |
| oz | `weightRaw / 100.0` oz (후보) | `flowRaw / 100.0` oz/s (후보) | 미확정(C-01-4, C-01-6) |

- 변환 배율은 단위별 상수 한 곳에 둔다.
- 유량은 저울이 계산한 "직전 1초 무게 증가량"이다(C-01-5). 컵을 올리는 순간처럼 무게가 갑자기 늘면 999(99.9 g/s)가 나온다(log:6735). 무게가 줄어도 0을 가정하지 않는다. 실측 규칙은 flow = clamp(w(t) − w(t−1 s), 0, 999)이고, 감소 중에도 1초 창 안의 증가분 때문에 0보다 클 수 있다(C-01-7, 감소 시 규칙 미확정(수정됨, 재검증 필요), 실측 96.9% 일치).
- 단위 미상 규칙(C-01-13, 미확정, 앱 규칙): 연결 직후 0x06 응답(Read 또는 Notify)을 받기 전에 도착한 0x01 프레임은 화면과 기록에 쓰지 않고 버린다. 디버그 로그에는 남긴다. 0x06 읽기는 연결 직후 보낸다.
- overload = 1이면 앱은 무게 대신 과부하 표시를 한다. 그 동안의 weightRaw 값은 쓰지 않는다(C-01-11 미확정).
- 음수 flowRaw는 그대로 디코딩한다. 실측에서 음수는 없었다. 앱의 유량 그래프는 음수를 0으로 표시한다(C-01-7, 앱 방어 규칙).
- 3599를 넘는 timerSec도 그대로 디코딩한다(C-01-9).
- 앱의 소수 초 표시는 앱 타이머가 만든다. 저울 타이머 해상도는 1 s다(C-01-8).

### 3.2 0x02 타이머 (원문 R/W/N, v1.0.4 실측 R/W)

상태 값(stateRaw): `01` 시작, `02` 일시정지, `03` 리셋 (C-02-1). 그 밖의 값은 디코더가 `TimerState{stateRaw}`에 raw 값 그대로 담고, 앱 상태 처리에서 무시한다(미확정, 앱 규칙. 실측 값은 01/02/03뿐).

| 방향 | opcode | length | payload | 비고 |
|------|--------|--------|---------|------|
| scale→App Notify | `01` | 1 | [stateRaw] | 원문: 상태가 바뀔 때 한 번 (C-02-2). TES017 v1.0.4에서는 오지 않음 |
| App→scale Read | `02` | 0 | — | `A55A020200000000` (log:3655) |
| scale→App Read 응답 | `02` | 1 | [stateRaw] | 조작 전 첫 Read `03`(전원 직후 값은 미확정), 시작 후 `01`, 일시정지 후 `02` (C-02-4) |
| App→scale Write | `03` | 1 | [action] `01`/`02`/`03` | 시작 `A55A03020001010000`(log:3894) / 일시정지 `…020000`(log:3957) / 리셋 `…030000`(log:3973) |
| scale→App Write 응답 | `03` | 1 | `00` 실패 / `01` 성공 | C-W-1. 뒤에 0x04 Notify가 붙을 수 있다(C-04-1) |

앱은 Write 응답 성공만으로 상태를 바꾼다. Write 뒤 0x02 Notify는 오지 않는다(C-02-3). 다른 펌웨어에서 0x02 Notify가 오면 그 값으로 덮어쓴다.

### 3.3 0x05 배터리 (R/N)

| 방향 | opcode | length | payload |
|------|--------|--------|---------|
| scale→App Notify | `01` | 2 | [bars uint8, percent uint8] |
| App→scale Read | `02` | 0 | — |
| scale→App Read 응답 | `02` | 2 | [bars uint8, percent uint8] |

- 실측: `A55A0105000203640000` = 3칸, 100 % (log:238). Notify는 30초마다(C-05-3).
- percent 0~100 (C-05-1). 디코더는 raw 값을 그대로 담고, UI는 100 초과 값을 100으로 표시한다(미확정, 앱 규칙. 실측 값은 100뿐).
- bars 범위는 미확정(C-05-2). 앱 UI는 percent만 쓴다.

### 3.4 0x06 단위 (R/W/N)

unitRaw: `00` g, `01` oz (C-06-1). 그 밖의 값은 단위 미상으로 두고 3.1의 단위 미상 규칙을 적용한다.

| 방향 | opcode | length | payload |
|------|--------|--------|---------|
| scale→App Notify | `01` | 1 | [unitRaw] |
| App→scale Read | `02` | 0 | — |
| scale→App Read 응답 | `02` | 1 | [unitRaw] |
| App→scale Write | `03` | 1 | [unitRaw] |
| scale→App Write 응답 | `03` | 1 | `00` 실패 / `01` 성공 |

- 실측 Read 응답 `A55A02060001000000` = g (log:3589).
- Write 성공 응답을 받으면 앱은 현재 단위를 바꾼다. 다음 0x01부터 새 단위로 변환한다. Write 수락 여부와 Write 후 Notify 여부는 미확정(C-06-2).
- 버튼에 의한 단위 Notify는 이 기기에 없다(C-06-3). 원문 형식대로 Notify를 디코딩할 수는 있게 둔다.

### 3.5 0x0B 전원 끄기 (W)

App→scale: opcode `03`, length 0 → `A55A030B00000000`. 응답: opcode `03`, length 1, `00`/`01` (C-0B-1). 실기기에 보낸 적 없다. 성공 후 연결이 끊기는 것은 정상이다. 앱은 이 끊김을 재연결 대상으로 보지 않는다.

전원 버튼으로 끄면 Notify 없이 약 2.1~2.2 s 뒤 연결 끊김이 감지된다(C-0B-2, macOS 측정). Android 감지 시간은 미확정이다(C-0B-2a, 프로브 B6). 앱은 이를 일반 연결 끊김과 구별할 수 없다.

### 3.6 0x0C 기기 이름 (R/W)

| 방향 | opcode | length | payload |
|------|--------|--------|---------|
| App→scale Read | `02` | 0 | — |
| scale→App Read 응답 | `02` | n | UTF-8 이름 n바이트 |
| App→scale Write | `03` | n (1~16) | UTF-8 이름 |
| scale→App Write 응답 | `03` | 1 | `00` 실패 / `01` 성공 |

- 실측 Read 응답: `A55A020C000C54494D454D4F52455F446F740000` = `TIMEMORE_Dot` (log:3623). Write는 실기기에 보낸 적 없다.

이름 쓰기 검증 (C-0C-1, C-0C-2):
1. 입력 문자열을 UTF-8로 인코딩한다.
2. 0바이트(빈 이름)이면 프레임을 만들지 않고 `InvalidName` 오류를 낸다.
3. 16바이트를 넘으면 16바이트 이하가 되도록 뒤에서부터 글자(코드 포인트) 단위로 자른다. 멀티바이트 글자를 중간에서 자르지 않는다. 예: `커피저울한글이름`(24바이트) → `커피저울한`(15바이트).
4. 최대 프레임 = 6 + 16 + 2 = 24바이트. 2.4 송신 규칙을 적용한다.

읽기 응답: n바이트 전체를 UTF-8로 디코딩한다. 잘못된 UTF-8은 대체 문자(U+FFFD)로 바꾼다. n은 16 이하로 가정하되 더 길어도 디코딩한다(C-0C-3).

### 3.7 0x0D 영점 (W)

App→scale: opcode `03`, length 0 → `A55A030D00000000` (F-7a, log:2102). 응답: opcode `03`, length 1, `00`/`01` → 실측 `A55A030D0001010000` (log:2104) (C-0D-1).

성공 응답 뒤 영점 전 무게(C-0D-2): 응답은 무게 알림 뒤에 붙어 오고(같은 알림의 무게는 영점 전 값), 그 뒤 무게 알림 2개도 영점 전 값이다. 0 g는 응답 알림 뒤 약 300 ms부터 온다. 실측 순서(log:13753-13756, 벡터 `rx-tare-preweight-seq-001`):

| 줄 | 시각 | 알림 내용 |
|----|------|-----------|
| 13751 | +309.539 | TX `A55A030D00000000` |
| 13753 | +309.667 | 무게 1450(145.0 g) + 응답 `A55A030D0001010000` |
| 13754 | +309.725 | 무게 1450 |
| 13755 | +309.844 | 무게 1450 |
| 13756 | +309.964 | 무게 0 |

log:2726-2729(213.4 g, 응답 → 0 g 300 ms)도 같은 모양이다. 앱은 응답만으로 영점이 무게에 반영됐다고 보지 않는다. 처리 규칙은 architecture.md 7.2를 따른다.

### 3.8 0x10 펌웨어 판 (R)

App→scale: opcode `02`, length 0. 응답: opcode `02`, length n, ASCII 문자열 (C-10-1). 실측 `A55A0210000676312E302E340000` = `v1.0.4` (log:3641). 비ASCII 바이트는 대체 문자로 바꾼다.

### 3.9 0x19 공장 초기화 (W)

App→scale: opcode `03`, length 0. 응답: opcode `03`, length 1, `00`/`01` (C-19-1). 실기기에 보낸 적 없다. 모든 설정이 지워진다. 앱은 사용자 확인 대화상자 없이 보내지 않는다.

### 3.10 0x1A 페어링 잊기 (W)

App→scale: opcode `03`, length 0. 응답: opcode `03`, length 1, `00`/`01` (C-1A-1). 실기기에 보낸 적 없다. 저울은 받은 뒤 자동 재부팅한다. 응답이 오기 전에 연결이 끊길 수 있으므로 앱은 끊김을 성공 후보로 다룬다. 사용자 확인 없이 보내지 않는다.

### 3.11 Write 응답과 시간 제한 (C-W-1, C-W-2)

- 응답 프레임: opcode `03`, 요청과 같은 cmd, length 1, payload `00` 실패 / `01` 성공(C-W-1). 다른 payload 값은 실패로 본다(C-W-1a, 미확정, 앱 규칙).
- 시간 제한: 1000 ms. 실측 응답 시간은 128~304 ms다(C-W-2). 넘으면 앱은 실패(`Timeout`)로 보고하고 재시도하지 않는다. 영점만 사용자 동작으로 다시 보낼 수 있다(C-W-2a, 미확정, 앱 규칙).
- Read 요청도 같은 시간 제한을 쓴다.

### 3.12 0x04 미상 Notify (scale→App, 원문 없음)

opcode `01`, cmd `04`, length `0x0005`, payload 5바이트 (C-04-1). 예: `A55A0104000500000000000000`.

| 직전 앱 동작 | 받은 0x04 payload | 근거 |
|--------------|-------------------|------|
| 타이머 Write 시작(리셋 상태에서) | `00 00000000` | log:3894 → log:3897 |
| 타이머 Write 일시정지(리셋 상태에서) | `01 00000000` | log:3675 → log:3677 |
| 타이머 Write 일시정지(동작 중) | 없음 | log:3957 → log:3959 |
| 타이머 Write 리셋 | `02 00000000` 다음 `01 00000000` | log:3713 → log:3715, log:3973 → log:3975 |

## 부록: 벡터 파일 키 (`protocol-vectors.json`)

- 최상위: `source`, `crc`, `vectors`.
- `crc` 블록(2026-10-28 프로브 A 반영으로 키 변경): `variant`(`"NONE"`), `rxCheck`(`false`, 수신 CRC 검사 안 함), `txValue`(`"0x0000"`), `byteOrder`, `range`, `status`, `firmware`(`"v1.0.4"`), `note`, `originalStated`(원문 기재 CRC: `name`, `poly`, `init`). 이전 키 `poly`·`init`·`refin`·`refout`·`xorout`는 최상위에서 뺐다.
- 상태: 모든 rx 벡터는 `confirmed`(CRC 미검사로 CRC 변형 의존이 사라졌다). 실기기에 보낸 바이트와 같은 tx 벡터 9건은 `origin: "device"`, `confirmed`. 실기기에 보내지 않은 tx(0x06 W, 0x0B, 0x0C W, 0x19, 0x1A)는 `unconfirmed`. `tx-name-write-empty-001`(프레임 없음)은 `confirmed`.
- 벡터 공통: `id`, `direction`(`rx`/`tx`), `hex`(문자열, 알림 여러 개(분할 또는 연속 알림 순서열)면 받은 순서대로 문자열 배열, 오류 기대 tx는 `null`), `origin`(`derived`/`device`), `status`(`confirmed`/`unconfirmed`), 선택 `evidence`(device 벡터의 로그 파일:줄).
- 모든 벡터의 CRC 자리는 `0000`이다. 예외: `rx-crc-bad-001`은 CRC `4106`을 그대로 두고 `WeightReport`를 기대한다. 수신 CRC를 검사하지 않는지 확인하는 벡터다.
- rx: `expect`는 객체 하나. 한 입력에서 프레임이 둘 이상 나오면 객체 배열. `unitContext`(`g`/`oz`)는 0x01 디코딩 당시의 현재 단위이며 raw 디코딩에는 영향이 없다.
- rx `expect.type`: `WeightReport{weightRaw, flowRaw, timerSec, overload}`, `TimerState{op, stateRaw}`, `Battery{op, bars, percent}`, `Unit{op, unitRaw}`, `WriteAck{cmd, success}`, `DeviceName{name}`, `FirmwareVersion{version}`, `Unknown{opcode, cmd, payloadHex}`. `op`는 `notify`/`read`. `payloadHex`는 대문자 hex. 오류는 `{error: "LengthMismatch", cmd, expectedLen, actualLen}`. `CrcMismatch`는 더 이상 기대하지 않는다.
- tx `command.type`: `ReadTimer`, `SetTimer{action: start|pause|reset}`, `ReadBattery`, `ReadUnit`, `SetUnit{unit: g|oz}`, `PowerOff`, `ReadName`, `SetName{name}`, `Tare`, `ReadFirmware`, `FactoryReset`, `ForgetDevice`. 오류 기대 tx는 `expect: {error: "InvalidName"}`.
